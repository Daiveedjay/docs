This page covers two separate team controls.

- **The agent handoff.** Owners and admins can decide whether coding agents, such as Claude Code or Cursor, may use Iris Code's agent tools on the team's code.
- **Pre-push records.** The team's record can note each time the pre-push check passed, and show when a pushed commit has no such record, so a person can look into it.

## The agent handoff

The agent handoff is the Iris Code MCP server. MCP is a connection that lets a coding agent call tools; through it, Iris Code gives the agent findings, file paths and short excerpts of code. What the agent then does with those results is governed by its own provider's data policies.

Turning the handoff off refuses every tool that reads the repository, including configuration and safe fixes. The agent receives the error `HANDOFF_FORBIDDEN`, with an explanation of who set the restriction.

A few things keep working, because they do not hand over repository content:

- `iris_check_package`, which checks a package name
- package guard agent hooks
- `iris rules`

## Policy levels

A restriction can be set at three levels. The table shows each setting and what it covers.

| Level | Setting | What it covers |
| --- | --- | --- |
| Organisation | Allow the agent handoff | No organisation restriction; project and repository restrictions still apply. |
| Organisation | Off for this team's projects | Repositories whose `.irisconfig.json` carries a registered Team `teamProjectId`. Unconnected repositories are outside this rule. |
| Organisation | Off on members' machines | Every repository on a machine signed in as an active member, including personal projects. |
| Project | Off for this project | An extra restriction for that registered Team project. Evidence being disabled does not remove it. |
| Repository | `"agentHandoff": false` | Everyone using the Iris Code MCP server for this repository, including signed-out and Free users. |

To change the organisation or project setting, open **Team settings > Agent handoff**. Members can see the setting; only an owner or admin can change it. Making it stricter or looser both ask for confirmation, and the workspace history records who changed it and what it was before and after.

Restrictions only add up, never cancel out:

- A project can follow the organisation setting or turn the handoff off. It cannot be more permissive than the organisation.
- In a repository, `"agentHandoff": true` or leaving the key out adds no restriction. Neither one can override a Team restriction.

## When changes take effect

The VS Code extension fetches the latest organisation and project settings when it starts, when its window regains focus, and every ten minutes while you are signed in and online.

Each agent tool call reads the most recently saved setting. A change therefore applies inside a running agent session once the editor has fetched it. A tool call that has already started finishes under the setting it started with.

The repository setting in `.irisconfig.json` is read on every tool call, so adding `false` takes effect on the next call. A restriction in a config file higher up the folder tree, or in the folder being checked, also applies.

The CLI can be used while signed out. Editors that are offline or signed out keep any restrictions they remember, under the seven-day rule described below.

Every active membership counts. Policy applies whether or not the member has Pro or an active seat, and if any of a person's teams restricts the handoff, the restriction wins. Invited people are not covered until they join.

## Offline and signed-out behaviour

Each time Iris Code successfully checks your licence, it saves the current policy in `~/.iris/governance.json`. VS Code, the CLI and JetBrains all share this file. A development build of the editor uses `governance.development.json` instead.

When the connection fails, the saved policy keeps applying:

- Signing out keeps the saved policy.
- Network failures, server errors and rate limiting keep the last confirmed policy.
- After seven days without a successful check, a machine that remembers any restriction refuses the handoff until it reconnects and checks again.
- Signing in successfully after leaving all organisations clears an old restriction.

These controls have limits. A machine that has never received a policy can only apply the repository setting. A different MCP server is outside these controls entirely. Someone who controls the machine can edit the saved file. This is a policy control with a record of who changed what, not copy protection.

## Pre-push hook records

The pre-push hook is a check that runs on a developer's machine when they push. After the whole local check passes, the hook records `hook_passed` for each commit and branch that Git handed to it. A failed scan or a failed package guard check records nothing.

Each record holds the commit identifier, branch and time. It contains no code, file paths or member identity. It is only sent when there is a licence, a `teamProjectId`, and project evidence is switched on.

Some further details:

- Records are kept under the normal Team evidence retention, currently 365 days. Once a record is removed it can no longer be found.
- The hook records up to ten pushed refs (branches or tags) each time it runs, and reports when more were pushed.
- If the record cannot be sent, an otherwise passing push still goes ahead.

Older hooks that lack the hook-source marker, which tells Iris Code the check is running for a push, must be reinstalled. `iris hook git status` tells you when that is needed.

## Verify in CI

You can check in CI whether a pushed commit has a pass record:

```sh
npx @iris-code/cli@latest hook verify . --sha "$PUSHED_COMMIT_SHA" --format json
```

`iris hook verify` needs Pro and a repository linked to a Team project. It looks for `hook_passed` against the full 40 or 64 character commit identifier.

If no record is found, it prints a warning and tries to add `hook_missing` to the Team audit log, shown as **Push with no hook record**. It always exits `0`, including when there is no licence or no network, so it never fails your build.

```yaml
- name: Check pre-push hook record
  if: always()
  run: npx @iris-code/cli@latest hook verify . --format github
  env:
    IRIS_LICENCE_TOKEN: ${{ secrets.IRIS_LICENCE_TOKEN }}
```

The command finds the commit to check on its own in common CI systems:

- GitHub pull requests use `pull_request.head.sha` from the event file, not the merge SHA in `GITHUB_SHA`.
- GitHub pushes use `GITHUB_SHA`.
- GitLab uses `CI_COMMIT_SHA`.
- Bitbucket uses `BITBUCKET_COMMIT`.

Other pipelines must pass `--sha`. An explicit SHA always takes precedence.

The command explains why it did not check when:

- the run has no licence, including fork pull requests without secrets;
- Pro entitlement cannot be established;
- the repository has no Team project binding or has invalid config;
- Team evidence is off or the run cannot access the project;
- the GitHub push deletes a branch, is made by a bot, or uses the `web-flow` committer;
- the event is unsupported, cannot be read, or contains no valid full commit identifier;
- another CI system did not supply `--sha`;
- Iris Code cannot be reached or the lookup response cannot be read.

## Read the evidence carefully

A missing record has several possible causes:

- the push used `--no-verify` to skip the hook
- the hook was not installed, or is an older version
- evidence is switched off
- the record failed to upload

So a missing record is a reason for a person to look at the push. It does not prove that someone skipped a check. This release does not fail a build or send email or Slack alerts for it.

The records are reported by members' own machines, not signed proof. An active member with a licence could send a pass record without running the hook. A record shows that a client reported a passing hook for that commit; it does not independently prove which files were checked.

Hook pass records are hidden from the audit event list by default. **Show hook passes** shows them. They are always included in CSV exports and in project counts for the selected date range.
