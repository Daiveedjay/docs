These are the commands you type in a terminal to use Iris Code. They set a project up, scan code, check packages and decide whether a project meets its standards. Anything marked **Pro** needs a licence. The other commands are Free: most work without an account, and the ones that scan a whole project use the monthly allowance that comes with a free sign-in.

Each command below starts with what it is for and when you would use it, followed by its options and exit codes.

## Common tasks

| Goal | Command | Next step |
|---|---|---|
| Set up a project | `iris init` | Review the generated settings |
| Scan one file | `iris check path/to/file.ts` | Review its score and findings |
| Check the project standard | `iris gate .` | Correct any failed thresholds; directory gates require Pro |
| Plan a refactor | `iris refactor path/to/file.ts` | Review suggestions before changing code |
| Check a package before installing | `iris install <package> --check` | Replace `<package>` with its name; this check installs nothing |

## Understanding command results

Every command returns a number when it finishes, called an exit code. A script, Git hook or CI pipeline reads it to decide whether to carry on. Each command's table below lists its own codes.

Every **Pro** command can also return `3`. That means you have a licence but it could not be checked, for example because the licence server could not be reached or it is limiting repeated requests. The command does not run, rather than skipping and reporting a success it has not earned.

Having no Pro licence is a different case. That is known, so those commands skip and exit `0`.

Some commands scan a whole project. On Free, each fresh project scan uses one action from your monthly allowance; Pro removes that monthly limit. This page calls either of these your project access. A scan's result is saved with an ID, called an evidence ID, and `--evidence <evidence-id>` opens it again without a new scan. See [Free allowances](/free).

`iris init` sets a project up. After that, `iris check` gives a score, and `iris gate` checks it in CI and fails the run when it falls short.

### iris init

Sets Iris Code up in a project in one step. Run it once when you start using Iris Code in a repository.

It asks three short questions, recommends a preset (a ready-made set of thresholds) and writes `.irisconfig.json`. It also installs the pre-push hook, a check that runs before `git push`, where the licence allows it, offers the [package guard](/agents/package-guard) for coding agents, and creates or refreshes the `AGENTS.md` rules block.

**Free**, except the Git hook step, which is Pro and is reported as skipped rather than failing the run.

| Flag | Description |
|---|---|
| `[path]` | Directory to set up (defaults to current directory) |
| `--yes`, `-y` | Take the Balanced preset without prompting. Also the behaviour when there is no terminal to ask at |

```bash
npx -y @iris-code/cli init
```

The questions cover what kind of project this is, what matters most right now, and whether Iris Code should block a push or only report. The answers map to one of the shipped presets, and the recommendation is shown with its reason before anything is written. You can always choose another preset from the list instead.

The package guard question defaults to yes when the project already shows a coding agent in use, such as a `CLAUDE.md` file or a `.cursor/` folder. With `--yes`, the guard is added only in that case.

Each step reports what it did:

```
Iris Code setup
  config: created .irisconfig.json with the Balanced preset
  git hook: skipped - Pro installs the pre-push gate; run `iris hook git install` after upgrading
  package guard: ready
  agent rules: created or refreshed Iris Code blocks
```

Running it again is safe. An existing `.irisconfig.json` is left alone rather than overwritten, and existing rules files have only their Iris Code block refreshed. A step that cannot complete is reported and skipped; it does not stop the other steps or fail the command.

### iris fix

Removes findings Iris Code can prove are safe to remove, such as a leftover debug statement or an unused variable. Use it to clear this kind of clutter from a file without editing it by hand.

**Free** for a single file. It shows a preview by default and never writes without confirmation.

| Flag | Description |
|---|---|
| `--safe <file>` | Required. Restricts the command to deterministic removals |
| `--apply` | Write the changes. Asks for confirmation first |
| `--yes`, `-y` | Answer that confirmation in advance. Required when there is no terminal to ask at |

```bash
# See what would be removed
iris fix --safe src/auth.ts

# Remove it, after confirming
iris fix --safe src/auth.ts --apply
```

Five kinds of fix qualify, and each can span several lines:

| Case | Example | Languages |
|---|---|---|
| A debug statement on its own | `console.log("debug", user)`, including a call split over several lines | All ten |
| An unused variable inside a function, assigned a literal | `const unused = 1` | JavaScript, TypeScript, Vue and Svelte scripts, Go, Python |
| A whole unused import | `import { a } from './a'` becomes `import './a'`, `import type { A } from './a'` and `import java.util.List;` are removed | JavaScript, TypeScript (`import type` only), Java |
| An unused name in an import that is otherwise used | `import { used, unused } from './a'` becomes `import { used } from './a'` | JavaScript, TypeScript |
| Two compatible imports from the same module | Two named imports from `./a` become one | JavaScript, TypeScript, Vue and Svelte scripts, Python, Rust |

Anything else is refused. Refusals are reported for each finding rather than for the whole run, so one finding that cannot be fixed does not stop the ones that can.

A hardcoded secret is never fixed automatically. The value has to move to the environment and the credential has to be replaced, and a fixer can do neither.

A debug statement sharing its line with real code is left alone, because deleting the line would take the code with it.

The fixer also refuses whenever removing something could change what the program does or leave it incomplete:

- `console.error` is never removed, because it reports real errors.
- A debug statement is kept if its arguments could do work, such as assigning a value, incrementing a counter, using `await` or calling something other than a simple formatter.
- It is also kept if it is the whole body of an `if`, `else`, loop or arrow function, or the last expression of a Ruby method.
- A removal is refused if it would leave a Go import or variable unused, or a Python block empty.
- A Python class attribute or module variable, a Go package variable, and a top-level variable in a JavaScript or TypeScript file without imports or exports are kept, because other code can read them. Unused literal-only function locals and eligible module variables can be removed.
- A TypeScript value import whose names are all unused is kept, because whether the module still loads depends on `verbatimModuleSyntax`. JavaScript keeps the load as `import './a'`.
- Imports in Vue and Svelte components are not removed, because the template can use a name the script check cannot see.
- Type-only TypeScript imports are not merged, and nor are Rust `use` statements that carry an attribute or doc comment.

The same fixes are offered as a Quick Fix in VS Code, through **Apply mechanical fixes** in the [refactor playbook](/refactor/overview), and through `iris_fix_safe` on the [MCP server](/agents/mcp). All of them use the same rules, so they agree on what is safe.

### iris refactor

Prints a refactor plan for one file. Use it when a file is too long or too complex and you want a concrete next step for yourself, a reviewer or a coding agent.

The plan lists the conventions the repository already follows, the mechanical fixes above, and ranked suggestions for restructuring the file, each with its evidence, risk and where the code would move. **Free**. The plan only reads your code; nothing is written.

| Flag | Description |
|---|---|
| `<file>` | Required. The source file to plan for |
| `--verify` | Compare the file with git HEAD and report `improved`, `not-improved` or `regressed`, with a correction |
| `--format <fmt>` | `text` (default) or `json` |

```bash
# Plan a refactor
iris refactor src/handlers.ts

# The full plan, for an agent
iris refactor src/handlers.ts --format json

# After editing, compare with the last commit
iris refactor src/handlers.ts --verify
```

Verifying one file without `--baseline` compares it with git HEAD, your last commit, including any uncommitted changes you already had.

A plan for several files saves a private baseline: a snapshot of the files when you planned, kept between CLI runs. Pass its returned ID with `--verify --baseline <baseline-id>` to verify that same piece of work without using another project action.

For a multi-file plan, run `iris refactor ./src --format json` and keep its `baseline_id`. Verify with `iris refactor ./src --verify --baseline <baseline-id>`. The [MCP server](/agents/mcp) and **Verify refactor** in the editor also keep the planned baseline. See [verifying a refactor](/refactor/verification).

Verification only reports: a `regressed` verdict does not change the exit code.

| Exit code | Meaning |
|---|---|
| `0` | Plan or verdict printed |
| `2` | Bad arguments, a missing file or a plan that could not be built |

### iris graph

Prints the import graph, the map of which files use code from which other files, that [Code Map](/features/code-map) draws in the editor. Use `--focus` before changing a file to see what it depends on and what depends on it.

Showing one focused file is Free. A fresh graph of the whole project uses your project access. `--evidence <evidence-id>` reads a saved graph without scanning again.

| Flag | Description |
|---|---|
| `--root <dir>` | Project root (defaults to current directory) |
| `--focus <file>` | One file: what it imports and what imports it **(Free)**. Without it, a captured whole-project graph or a fresh project inspection |
| `--format <fmt>` | `text` (default) or `json` |
| `--include-external` | With `--focus`, also list packages and built-in modules |

```bash
# One file's imports and importers (free)
iris graph --focus src/app.ts

# Inspect the whole graph as JSON, using project access
iris graph --format json
```

It reads TypeScript, JavaScript, Vue, Svelte, Go, Python, Java, C# and Rust. It works out where each import points in the same way as the editor and skips the same `ignoreFiles`.

An import Iris Code cannot trace to a file is listed with its reason, for example `missing-file` or `ambiguous-target`, and is never guessed at. Go and Java packages and C# namespaces appear as their folders, because that is what those imports name.

An import graph only shows imports. Files in the same Go or Java package, C# namespace or Rust module can use each other without one, so those uses do not appear, and the text output says so when the project has such files.

The JSON carries `schemaVersion: 1`. The whole graph is `{ schemaVersion, root, graph }`; with `--focus` it is `{ schemaVersion, root, focus, view, unresolved }`, and `unresolved` holds only that file's entries.

| Exit code | Meaning |
|---|---|
| `0` | Graph printed, whether or not some imports were unresolved |
| `1` | The graph could not be built |
| `2` | Bad arguments, a `--focus` file outside the root, or a file the graph does not read |

### iris schema

Prints the [Schema graph](/features/schema-graph): your database tables, their columns and how they link, using the table and column names read from their declarations in your project. Use it to see your data model, or add `--usage` to see where the code uses a table.

The structure, and usage for one focused table, are Free. Usage across all tables can come from a saved result with `--evidence <evidence-id>`; otherwise a fresh project scan uses your project access.

```bash
iris schema . --format json
iris schema . --table users --usage
iris schema . --format dbml
```

| Argument or flag | Meaning |
| --- | --- |
| `[path]` | Project directory, defaults to the current directory |
| `--format <format>` | `text` (default), `json`, `mermaid` or `dbml` |
| `--table <name>` | Focus a database name, model name or canonical table ID and its neighbours |
| `--usage` | Include usage and warnings; all-table usage uses captured project evidence or a fresh project action |

JSON carries `schemaVersion: 1`.

References Iris Code could not resolve, disagreements between sources and statements it did not read are reported for information only, so a successful run exits 0. Invalid arguments, or a table that is unknown or matches more than one name, exit 2. A build error exits 1.

Use `--evidence <evidence-id>` to read usage across all tables from a result you own without scanning again. Without an evidence ID or `--table`, the command checks your project access before starting a fresh scan.

### iris check

Scores source files and prints their findings. Use it on one file while you work, or on a folder to see how a whole area of the project stands.

Checking a single file is Free. `iris check . --inspect` runs a one-off scan of the project using your project access. Using a directory, staged files or changed files as enforcement, a check that fails so the next step stops, still needs paid access. An inspection does not install or run a blocking hook.

| Flag | Description |
|---|---|
| `[path]` | File or directory to scan (defaults to current directory) |
| `--staged` | Scan staged git files only **(Pro)** |
| `--changed` | Scan files changed since the last commit **(Pro)** |
| `--min-score <n>` | Minimum health score 0–100; overrides `.irisconfig.json` |
| `--config <path>` | Use a specific `.irisconfig.json` |
| `--format <fmt>` | Output format: `pretty` (default), `json`, or `github` |
| `--output <path>` | Write JSON result to file (requires `--format json`) |
| `--verbose` | Show individual findings per file |
| `--show-suppressed` | List each finding suppressed by an `iris-ignore` comment, with its reason |
| `--slack-on <when>` | `failure` (default) or `always` |
| `--slack-dry-run` | Print the Slack payload instead of posting it |

Findings silenced by [inline suppressions](/enforcement/suppressions) (`// iris-ignore: <ruleId> -- <reason>`) do not count against the score. The number suppressed always appears in the output, `--show-suppressed` lists each one, and JSON reports include a `suppressed` array for each file.

Directory checks also find [duplicate code blocks](/features/duplicate-detection) across files, and each JSON file entry includes a `duplicateBlocks` array. Files left out of the duplicate comparison, because they are too large or look minified, are listed in the output rather than skipped silently.

```bash
# Score a single file (free)
iris check src/index.ts

# Score a directory with a custom threshold (Pro)
iris check src/ --min-score 80

# Score staged files only (Pro)
iris check --staged
```

| Exit code | Meaning |
|---|---|
| `0` | All files at or above threshold |
| `1` | One or more files below threshold |
| `2` | Bad arguments or config error |

### iris secrets

Scans the project for credentials written into the code, such as API keys, tokens and passwords. Run it before you push, or in CI, so a secret is caught before it is shared. **Free - no authentication required.**

| Flag | Description |
|---|---|
| `[path]` | File or directory to scan (defaults to current directory) |
| `--history` | Scan the git commit history instead of the working tree (**Pro**) |
| `--depth <n>` | With `--history`: commits to walk (default `50`; `0` = full history) |
| `--format <fmt>` | Output format: `pretty` (default) or `json` |
| `--output <path>` | Write JSON result to file (requires `--format json`) |

```bash
# Scan the current directory
iris secrets

# Scan a specific path and output JSON
iris secrets ./src --format json

# Scan the last 50 commits of git history (Pro)
iris secrets --history

# Scan the full history
iris secrets --history --depth 0
```

`--history` finds secrets that were committed and later removed. Every file version added by each commit, committed `.env` files included, goes through the same two-layer detection as your current files.

Each distinct secret is reported once and always masked. The report shows when it was first and last seen, the commits and files involved, and whether the secret is still in your latest commit (HEAD).

Merge commits are covered. Limits on what was checked, such as the depth, size caps and shallow clones (copies made without the full history), are always shown, so a clean result never suggests the whole history was checked when it was not.

Everything runs against your local Git history; nothing leaves the machine. The real fix is to replace the credential: a secret that reached history should be rotated even if it was later removed.

| Exit code | Meaning |
|---|---|
| `0` | No secrets found |
| `1` | Secrets found (working tree, or anywhere in the scanned history range) |
| `2` | Bad arguments |

### iris security

Scans the project for nine risky coding patterns that often lead to security problems. Use it alongside `iris secrets` to catch them before they ship. **Free - no authentication required.**

The patterns are:

- `eval` or `exec` usage, which runs text as code
- SQL built by joining strings together
- insecure random number generation
- regular expressions that can be made to run extremely slowly (ReDoS)
- hardcoded `localhost` URLs
- disabled TLS certificate checks
- debug flags left switched on
- weak hashing (MD5 or SHA-1)
- open redirects

See [Security Smells](/features/security-smells) for the full pattern reference.

| Flag | Description |
|---|---|
| `[path]` | File or directory to scan (defaults to current directory) |
| `--format <fmt>` | Output format: `pretty` (default) or `json` |
| `--output <path>` | Write JSON result to file (requires `--format json`) |

```bash
# Scan the current directory
iris security

# Scan a specific path and output JSON
iris security ./src --format json
```

| Exit code | Meaning |
|---|---|
| `0` | No security smells found |
| `1` | Security smells found |
| `2` | Bad arguments |

### iris deps

Checks the packages your project depends on for newer versions and known CVEs, the published security advisories in the [OSV.dev](https://osv.dev) database. Use it to see what needs updating and what has a known vulnerability.

It covers npm, Go, Python, RubyGems, NuGet, Cargo and Maven or Gradle projects. Nested Go, Python and Ruby projects in a monorepo are read too, and each of their packages is tagged with its folder.

A fresh audit you choose to run uses one project action when it succeeds. A saved audit that is still valid, with nothing changed, can be reused; `--no-cache` asks for fresh results instead. Opening saved data does not look anything up again.

When your project has a lockfile, the installed versions are read from it, for example `package-lock.json` v1-v3, `pnpm-lock.yaml`, `yarn.lock` classic and Berry, `bun.lock`, `poetry.lock`, `Pipfile.lock`, `uv.lock`, `Gemfile.lock`, `packages.lock.json` and `Cargo.lock`. The audit then reflects what is actually installed rather than the range in the manifest, and advisories are matched to that installed version.

Monorepo workspace members (npm and yarn workspaces, `pnpm-workspace.yaml`) are found and counted once automatically, and internal `workspace:` / `file:` / `link:` dependencies are left out.

| Flag | Description |
|---|---|
| `[path]` | Directory to scan (defaults to current directory) |
| `--no-cache` | Skip the 24-hour local cache and re-fetch |
| `--verbose` | Show individual CVE titles and URLs |
| `--format <fmt>` | Output format: `pretty` (default) or `json` |
| `--output <path>` | Write JSON result to file (requires `--format json`) |
| `--allow-network` | Re-enable network lookups after a revoke |
| `--revoke-network` | Disable version and advisory lookups |

```bash
# Audit dependencies in the current project
iris deps

# Bypass the cache and output JSON
iris deps --no-cache --format json
```

The first lookup over the network asks for your permission and shows exactly what is sent: package names and versions, nothing else. Your choice is saved in `~/.iris/preferences.json`. Run with `--revoke-network` to turn lookups off later, or `--allow-network` to turn them back on. When results come from the 24-hour cache, the output shows how old the cached scan is.

No token or rate-limit setup is needed. OSV.dev lookups need no account, and only the package name, ecosystem and version are sent.

Each advisory in the output carries a confidence label (`fix-available`, `direct`, `transitive`, or `manual-review`) and, where one exists, the version that fixes it.

Advisories without a verifiable ID or severity are never shown. They are left out, and the output says how many were skipped. A dependency whose lookup failed is marked "not checked", never assumed clean.

| Exit code | Meaning |
|---|---|
| `0` | No vulnerabilities found |
| `1` | One or more vulnerabilities detected |
| `2` | Invalid arguments or no manifest found |

### iris cve

**Pro.** Runs the same dependency and CVE scan as `iris deps`, sharing its 24-hour cache and network permission, but exits `1` only when it finds a vulnerability at or above the `--severity` level.

This is the command for a CI gate: it can block merges on high or critical advisories without failing the pipeline over minor ones. Each matched advisory shows its confidence label (`fix-available`, `direct`, `transitive`, or `manual-review`) and, where one exists, the version that fixes it.

| Flag | Description |
|---|---|
| `[path]` | Directory to scan (defaults to current directory) |
| `--severity <lvl>` | Minimum severity that fails the run: `low`, `medium`, `high` (default), or `critical` |
| `--no-cache` | Skip the 24-hour local cache and re-fetch |
| `--format <fmt>` | Output format: `pretty` (default) or `json` |
| `--output <path>` | Write JSON result to file (requires `--format json`) |
| `--allow-network` | Re-enable network lookups after a revoke |
| `--revoke-network` | Disable version and advisory lookups |

```bash
# Fail on high or critical advisories (default threshold)
iris cve

# Gate on critical advisories only
iris cve --severity critical

# Include everything, down to low severity
iris cve --severity low
```

| Exit code | Meaning |
|---|---|
| `0` | No CVEs at or above the threshold |
| `1` | One or more CVEs at or above the threshold |
| `2` | Invalid arguments or no manifest found |

A package reported in the OpenSSF malicious-packages feed fails the run at every `--severity` level and is listed under its own **MALICIOUS** heading. Those reports carry no severity score of their own, so without this rule they would rank below `low`.

### iris install

**Free.** Checks each package before it is installed, then installs it with the project's own package manager, found from its lockfile. Use it in place of your usual install command when you want a package checked first.

It checks for known vulnerabilities, malicious-package reports, yanked, deprecated and prerelease versions, and brand-new releases. See the [package guard](/agents/package-guard) for what each verdict means.

With no package names, it checks the whole project first: every package the lockfile would install, and the repository's own install scripts, which it shows and asks about before running the install. This is the check to run on a repository you have cloned and do not yet trust. See [Installing a whole project](/agents/package-guard#installing-a-whole-project).

`iris add` and `iris i` are other names for the same command.

| Flag | Description |
|---|---|
| `<package[@version]...>` | One or more packages, with an optional version, range or tag. Omit to check and install the whole project |
| `--ignore-scripts` | Whole project: install without running the project's own install scripts |
| `--yes`, `-y` | Whole project: run the project's install scripts without asking |
| `-r`, `--requirement <file>` | Whole project, pip and uv: the requirements file to install |
| `--manager <name>` | Use this package manager instead of the detected one |
| `--check` | Check only; install nothing. `--dry-run` is accepted as another name |
| `--force` | Install even when a package is blocked, printing what was overridden |
| `--format json` | Print the verdicts as JSON, with every advisory |
| `--verbose` | List every known vulnerability, with links. Otherwise the five worst are shown and the rest counted |
| `--no-cache` | Ignore the local package cache |
| `--allow-network` / `--revoke-network` | Turn network lookups on or off |

```bash
iris install lodash@4.17.20
iris install requests --check
iris install                  # the whole project
iris install --check          # the whole project, install nothing
```

| Exit code | Meaning |
|---|---|
| `0` | Installed, or clean with `--check` |
| `1` | Blocked or cancelled; nothing was installed |
| `2` | Invalid arguments or no package manager found |

### iris remove

**Free.** Removes packages with the project's own package manager: `npm uninstall`, `pip uninstall`, `cargo remove`, `bundle remove`, `dotnet remove package`, `go get <module>@none` and so on. It saves you remembering each package manager's remove command.

Nothing is checked, because removing a package is never the risk the guard is for. A version is ignored, so the spec you passed to `iris install` works as it is. `iris uninstall` and `iris rm` do the same.

| Flag | Description |
|---|---|
| `<package...>` | One or more packages |
| `--manager <name>` | Use this package manager instead of the detected one |
| `--dry-run` | Print the command without running it |

```bash
iris remove lodash
iris rm requests==2.19.0
```

If the package manager itself fails, its exit code is passed through.

### iris sbom

**Free.** Exports a software bill of materials (SBOM): a list of every package your project uses, in the CycloneDX 1.5 format that security and compliance tools read. It covers npm, Go, Python, RubyGems, NuGet, Cargo and Maven manifests in the project.

Exporting from your manifests looks nothing up in a registry or advisory database, so it does not ask for network permission. When it reuses a saved audit that belongs to your account, it checks online that the audit is yours; a saved result already confirmed as yours can also be read offline.

Each component carries the package name, the exact installed version (read from the lockfile), a `purl` (a standard package identifier), and a `required` or `optional` scope depending on whether the dependency is direct or for development only. If a cached `iris deps` scan exists, its known vulnerabilities are added as CycloneDX `vulnerabilities` entries, linked to each package by its `purl`.

Some dependencies have no version to report: a NuGet `PackageReference` with no version and no Central Package Management entry, or two projects pinning different versions of the same package. Those components are still listed, because an SBOM that quietly leaves out a dependency is worse than one that admits it does not know the version.

They carry a `purl` without a version, such as `pkg:nuget/CsvHelper`, no `version` field, and an `iris:version-unresolved` property naming the reason. A purl with an invented version would look valid, so a scanner reading it would fail to match the package without reporting a problem.

| Flag | Description |
|---|---|
| `[path]` | Directory to scan (defaults to current directory) |
| `--output <path>` | Output file path (default: `./iris-sbom.json`) |
| `--stdout` | Print the SBOM to stdout instead of writing a file |

```bash
# Write iris-sbom.json in the current directory
iris sbom

# Print the SBOM to stdout for piping into other tools
iris sbom --stdout
```

| Exit code | Meaning |
|---|---|
| `0` | SBOM generated successfully |
| `2` | Invalid arguments or no manifest found |

| Flag | Description |

| `--format <fmt>` | Output format: `pretty` (default) or `json` |
| `--output <path>` | Write JSON result to file (requires `--format json`) |

```bash
# List all TODO/FIXME/HACK comments in the project
```

### iris gate

**Pro.** Checks the project against every threshold configured in `.irisconfig.json`, including `gateMaxNamingViolations`, and shows each threshold beside its actual value with a PASS or FAIL. This is the recommended command for CI, because it exits `1` when any rule fails and so stops the pipeline.

There is no command-line flag to override thresholds; set them in `.irisconfig.json`.

Findings silenced by [inline suppressions](/enforcement/suppressions) (`// iris-ignore: <ruleId> -- <reason>`) do not count against gate rules, but the number suppressed always appears in the output. Set `gateMaxSuppressions` to cap suppressions per file, or `ignoreSuppressions: true` to ignore every suppression comment so suppressed findings count again.

| Flag | Description |
|---|---|
| `[path]` | File or directory to scan (defaults to current directory) |
| `--config <path>` | Use a specific `.irisconfig.json` |
| `--format <fmt>` | Output format: `pretty` (default), `json`, or `github` |
| `--output <path>` | Write JSON result to file (requires `--format json`) |
| `--show-suppressed` | List each finding suppressed by an `iris-ignore` comment, with its reason |
| `--slack-on <when>` | `failure` (default) or `always` |
| `--slack-dry-run` | Print the Slack payload instead of posting it |

```bash
# Run the gate against the configured thresholds
iris gate

# Emit inline PR annotations in GitHub Actions format
iris gate . --format github

# Post the outcome to a Slack channel from your own CI
IRIS_SLACK_WEBHOOK="$SLACK_WEBHOOK_URL" iris gate .
```

| Exit code | Meaning |
|---|---|
| `0` | All rules pass |
| `1` | One or more rules fail |
| `2` | Bad arguments or config error |
| `3` | Licence could not be verified, so the gate did not run |

### iris slack

Sets up and tests Slack notifications, so the result of `iris check` or `iris gate` is posted to a channel your team reads. The command is **Free**. Iris Code reads the webhook (the address Slack gives you for posting messages) only from `IRIS_SLACK_WEBHOOK`, and sends messages directly from your machine or CI.

| Subcommand | Description |
|---|---|
| `iris slack setup` | Validate a webhook, send a test message, and show the CI secret configuration |
| `iris slack test` | Send a test message using `IRIS_SLACK_WEBHOOK` |
| `iris slack manifest` | Print a link and manifest for creating a pre-configured Slack app |

The complete setup, what each message contains and how the webhook is handled are covered in [Slack notifications](/enforcement/slack-notifications).

### iris rules

Writes this project's configured thresholds, taken from `.irisconfig.json`, into the file your coding agent already reads, so the agent knows your limits before it writes code. **Free.** Nothing is analysed, nothing is sent anywhere, and no model is involved.

| Flag | Description |
|---|---|
| `--target <name>` | `agents` (default, `AGENTS.md`), `claude`, `cursor`, or `copilot`. May be repeated to write several files |
| `--all` | Write all four target files |
| `--refresh` | Update only the target files this repository already has, and create none |
| `--dry-run` | Print what would be written instead of writing it |
| `--yes`, `-y` | Do not ask before updating a file that already exists |

A project using two agents may need two files. Claude Code reads only `CLAUDE.md`, while `AGENTS.md` is the default shared target, and Cursor and Copilot have their own target files too. Each file is written separately, so one damaged file is reported and skipped while the rest still update.

The rules go between `iris-rules` markers, so regenerating updates only Iris Code's own section and never your text. Full behaviour, including what the file contains and what happens to a damaged marker, is in [Project rules](/agents/project-rules).

### iris mcp

Runs Iris Code as an MCP server. MCP is a connection that lets a coding agent call tools, so the agent can check files and read your project's rules itself while it works. The server talks to the agent over standard input and output.

Basic file checks, configuration, one-file fixes and plans, focused schema information and the package guard are Free. Fresh project scans, dependency audits and multi-file plans use your project access; reading a result you already earned does not use it again. Fresh enforcement still needs paid access. See [MCP tools](/agents/mcp#tools).

| Flag | Description |
|---|---|
| `--root <path>` | Pins the directory the server may read. Every requested path must resolve inside it, symlinks included. Omit it and Iris Code asks your editor which project is open, falling back to the launch directory |
| `--sdk` | Serve the same tools through the official MCP TypeScript SDK instead of the built-in transport |

```bash
# Run the server; your editor tells it which project is open
npx -y @iris-code/mcp

# Equivalent, with the CLI already installed
iris mcp
```

Leave out `--root` unless you specifically need the folder pinned. Passing it stops Iris Code asking your editor, so a single pinned setup shared across several projects answers every one of them about the folder named in the flag. `--root .` in particular pins nothing: it is the launch directory, which is already the fallback.

The server writes only protocol messages to standard output, so it must not be wrapped in a script that prints anything there. Editors bundling the Iris Code language-server binary can use `iris-lsp --mcp` instead, with no Node.js install.

Tool-by-tool behaviour, the preview token a fix needs before it is written, and the limits on response size are in [MCP server](/agents/mcp).

### iris report

Exports a report of a scan that you can share with people who do not use Iris Code. It writes HTML by default, or a PNG or SVG card, or selected PDF pages.

`--evidence <evidence-id>` exports a saved result you own without scanning your current files. Existing anonymous introductory cards and PDFs remain readable. A fresh directory scan uses your project access; an HTML report for a single file stays Free.

| Flag | Description |
|---|---|
| `[path]` | File or directory to scan (defaults to current directory) |
| `--output <path>` | Output file path (default: `./iris-report.html`) |
| `--config <path>` | Use a specific `.irisconfig.json` |
| `--min-score <n>` | Health score threshold 0-100 |
| `--format <format>` | `html` (default), `png`, `svg` or `pdf` |
| `--size <size>` | Card layout: `portrait` (default) or `landscape` |
| `--pages <selection>` | PDF only: `summary`, `full` (default), or comma-separated page IDs |
| `--include-paths` | Include relative file names when Where to look is selected |

The PDF page IDs, in output order, are `summary`, `findings`, `areas`, `standard`, `trend` and `dependencies`.

- Summary is always included.
- Full includes the first four sections, plus the trend when it is available. Dependencies is only included when you ask for it.
- Standard continuation pages keep their section number.
- Trend needs more than one saved scan, and Dependencies needs a saved dependency audit.

```bash
# Export a report to the default location
iris report

# Export a report to a custom path
iris report --output ./reports/latest.html

# Export one PDF page
iris report --format pdf --pages summary

# Export selected sections, with Summary included automatically
iris report --format pdf --pages standard,trend
```

Full writes `iris-report.pdf`, Summary writes `iris-report-summary.pdf`, and Custom writes `iris-report-custom.pdf` unless you use `--output`. Cards are named by size, such as `iris-report-portrait.png`.

A page you list in `--pages` that the scan cannot provide prints `Left out <id>: <reason>` to stderr, and the export still exits 0 if it succeeds. Full includes the score trend only when there is saved history, and prints no notice when it leaves it out. An unknown page ID, or `--pages` with HTML, PNG or SVG, exits 2.

| Exit code | Meaning |
|---|---|
| `0` | Report written successfully |
| `2` | Bad arguments or could not write the file |

### iris hook

Installs and removes two checks that run automatically: the Git pre-push hook, which runs before each `git push`, and the build hook, which runs as part of your project's build. These do the same as the hook commands in the VS Code command palette. It also manages the package guard hook for coding agents.

The type (`git`, `build` or `agent`) comes before the action. `status` and `uninstall` are **Free**, including after a licence expires or while offline. Installing a Git or build hook that blocks needs paid access for the selected project.

| Subcommand | Description |
|---|---|
| `iris hook git status [path]` | Show whether the git pre-push hook is installed **(free)** |
| `iris hook git install [path]` | Write the Iris Code block to the active pre-push hook **(Pro)** |
| `iris hook git uninstall [path]` | Remove the Iris Code block from the active pre-push hook **(Free)** |
| `iris hook build status [path]` | Show whether the build hook is installed **(free)** |
| `iris hook build install [path]` | Wire Iris Code into the project build command **(Pro)** |
| `iris hook build uninstall [path]` | Remove the Iris Code build entry **(Free)** |
| `iris hook agent install [path]` | Add the [package guard](/agents/package-guard) hook for Claude Code, Cursor, Codex, GitHub Copilot, Gemini CLI or Windsurf **(free)** |
| `iris hook agent uninstall [path]` | Remove the package guard hook **(free)** |
| `iris hook agent status [path]` | Show whether the package guard hook is installed **(free)** |

The active pre-push hook is `.git/hooks/pre-push`, unless Git's `core.hooksPath` setting points elsewhere. With Husky, the block goes in `.husky/pre-push` rather than Husky's generated files.

`iris hook agent` takes these options:

- `--target` with `claude`, `cursor`, `codex`, `copilot`, `gemini`, `windsurf`, a comma-separated list of them, or `all`. Without it, install picks the agents the project already shows signs of, or Claude Code.
- `--yes` to skip the confirmation when a settings file already exists.
- `--dry-run`.
- `--verify-on-finish`, which adds the optional [finish verification](/refactor/verification) hook for every agent except Windsurf.

```bash
# Check current hook status (free)
iris hook git status

# Install the git pre-push hook
iris hook git install

# Remove the build hook
iris hook build uninstall
```

| Exit code | Meaning |
|---|---|
| `0` | Success |
| `2` | Bad arguments, not a git repository, or no project manifest found |

### iris config

Creates or checks `.irisconfig.json`, the file that holds your project's thresholds. Use `init` to create one from a preset, and `validate` to find mistakes in one you have edited.

| Subcommand | Flag | Description |
|---|---|---|
| `init [path]` | - | Interactively pick a preset (`legacy`, `balanced`, `strict`, `security`, `typescript`, `ai-assisted`) and write `.irisconfig.json`. Pro users are also prompted for gate limits. Falls back to a non-interactive `balanced` default when stdin is not a TTY (e.g. in CI). |
| `validate [path]` | - | Validate an existing `.irisconfig.json` and print any schema or value problems |


| Exit code | Meaning |
|---|---|
| `0` | Success / no validation issues |
| `1` | `validate` found error-severity problems |
| `2` | Bad arguments, or `init` found an existing file with no TTY to confirm overwrite |

### iris hook verify

```sh
npx @iris-code/cli@latest hook verify [path] --sha <full-commit-id> --format pretty
```

**Pro.** Run in CI for a Team project, it checks the Team's records for a passing pre-push hook run on a pushed commit. Formats: `pretty`, `json`, `github`. `--sha` is optional on supported CI providers.

When there is no record, it warns and tries to write a **Push with no hook record** entry. Unlike the other Pro commands, it always exits `0`, including for a missing licence, invalid arguments and network failures.

See [Team governance](/teams/governance) for how the commit is found and every reason a check can be skipped.

## iris usage

Shows your account's or team's allowance and the results saved on this machine. It does not start a scan.

```bash
iris usage status
iris usage results
iris usage result <evidence-id>
iris usage recover
```

`recover` matches recorded actions with their outcomes, and leaves any whose outcome is still unknown waiting for confirmation. See [Free allowances](/free) for offline access and the commands for saved results.

A result opened with `--evidence` keeps the project folder and configuration it was scanned with. If you also give a path, it must match that folder; leave the path out to read a result from another working directory. With a saved graph, a `--focus` path is looked up inside the saved project folder.

## Verification integrity

`iris check . --integrity` checks whether your current changes weaken your tests or rules, such as a deleted or skipped test or a lowered threshold, compared with your last commit. It is Free.

- `--from <revision>` compares with another branch or commit instead.
- `--staged` compares exactly what you have staged with `git add` against your last commit.
- `--from` and `--staged` cannot be used together.
- `--format json` adds an `integrity` report with the findings, how many block, and anything that could not be checked.

A blocking finding exits 1, a clean comparison exits 0 and a bad flag exits 2. Score scans keep their usual access requirements. `iris gate . --from <revision>` also checks for weakened tests and rules against that revision before it checks scores.

See [verification integrity](/features/verification-integrity).
