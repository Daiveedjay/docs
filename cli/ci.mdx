Continuous integration (CI) runs automated checks every time your code changes. Adding the Iris Code gate means each change is checked against your project's thresholds alongside your other tests, and a change that falls short fails the build.

The gate runs on your own CI machine, called a runner, so your source code stays there. Install the CLI, store your Pro licence as a CI secret and run `iris gate`. The command returns a number, called an exit code, that tells the pipeline whether to continue.

## Exit codes

Your pipeline decides whether to carry on from the exit code. `iris gate` uses the same codes as every other Iris Code command:

| Exit code | Meaning | Pipeline action |
|---|---|---|
| `0` | All gate rules pass | Pipeline continues |
| `1` | One or more gate rules failed: the `minHealthScore` threshold or any configured `gateMax*` limit (`gateMaxSecrets`, `gateMaxComplexity`, `gateMaxFileLength`, `gateMaxSmellsPerFile`, `gateMaxSecuritySmells`) | Fail the build |
| `2` | Bad arguments or invalid config | Fix the workflow step |
| `3` | Your Iris Code licence could not be verified, so the gate did not run | Fail the build, or retry |

Exit `3` means the gate **did not run**, which is not the same as it finding nothing. It is returned when you have a licence but it could not be checked, for example because the licence server could not be reached or it is limiting repeated requests.

A gate that quietly skipped and reported success would let through a build that should have been stopped. So when the licence cannot be checked, the build fails instead.

Having no Pro licence is a different case. That is known, so those commands skip and exit `0`, and the pipeline stays green.

## Setting IRIS_LICENCE_TOKEN

Add your licence key as a secret in your CI provider's settings, then pass it as the `IRIS_LICENCE_TOKEN` environment variable in the step that runs Iris Code. The CLI checks this variable before reading the credentials file, so runners need no `iris auth login` step. See [Authentication](/cli/auth) for how the CLI signs in.

<Note>
  `iris secrets` and `iris security` need no sign-in at all. Use them for a Free CI scan that needs no licence: they work on any runner, whether or not `IRIS_LICENCE_TOKEN` is set.
</Note>

## GitHub Actions

The example below shows a minimal `iris gate` step. For the full workflow including branch protection rules and threshold configuration, see the [GitHub Actions](/enforcement/github-actions) guide.

```yaml
name: Iris Code scan
on: [push, pull_request]

jobs:
  iris:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with:
          node-version: 20
      - run: npm install -g @iris-code/cli
      - name: Gate check
        run: iris gate
        env:
          IRIS_LICENCE_TOKEN: ${{ secrets.IRIS_LICENCE_TOKEN }}
```

<Note>
  For inline PR annotations, use `iris gate . --format github` (added in v1.6.0). See the full guide at [/enforcement/github-actions](/enforcement/github-actions).
</Note>

To add the Free secrets and security scans, which need no licence, include these steps separately:

```yaml
      - name: Secrets scan (free, no licence)
        run: |
          npm install -g @iris-code/cli
          iris secrets

      - name: Security smell scan (free, no licence)
        run: |
          npm install -g @iris-code/cli
          iris security
```

## Gating on dependency CVEs

A CVE is a published security advisory for a package. Use `iris cve` (Pro) as a separate gate for your dependencies. It runs the same scan as `iris deps` but exits `1` only when it finds an advisory at or above the severity you choose, so minor advisories never fail the pipeline:

```yaml
      - name: CVE gate
        run: iris cve --severity high
        env:
          IRIS_LICENCE_TOKEN: ${{ secrets.IRIS_LICENCE_TOKEN }}
```

See the [command reference](/cli/commands#iris-cve) for severity levels and exit codes.

## Telling the team in Slack

A result written only to the build log is seen only by whoever opens that log. Set `IRIS_SLACK_WEBHOOK` as a protected CI secret and the outcome is posted to a Slack channel as well:

```yaml
      - name: Iris Code gate
        run: iris gate . --format github
        env:
          IRIS_LICENCE_TOKEN: ${{ secrets.IRIS_LICENCE_TOKEN }}
          IRIS_SLACK_WEBHOOK: ${{ secrets.IRIS_SLACK_WEBHOOK }}
```

Your own runner builds and sends the message, and it never passes through Iris Code servers, so it can name the failing files. Nothing is posted for a passing run unless you add `--slack-on always`, and a Slack outage never changes the exit code. See [Slack notifications](/enforcement/slack-notifications) for the full setup.

## GitLab CI

```yaml
iris-gate:
  stage: test
  image: node:20
  script:
    - npm install -g @iris-code/cli
    - iris gate
  variables:
    IRIS_LICENCE_TOKEN: $IRIS_LICENCE_TOKEN
```

## Generic shell

For any CI environment that runs arbitrary shell scripts:

```bash
#!/bin/sh
set -e
npm install -g @iris-code/cli
iris gate
```

<Note>
  `iris gate` has no threshold flag. Set `minHealthScore`, and any `gateMax*` limits, in `.irisconfig.json` instead. See [.irisconfig.json](/configuration/irisconfig) for the full reference.
</Note>

<Tip>
  Pair `iris gate` (Pro) with `iris secrets` (Free) so each covers what the other does not. The gate stops code that misses your thresholds, and the secrets scan catches leaked credentials on every push, whatever your licence status.
</Tip>

## Check the pre-push hook record

A pre-push hook is a check that runs on a developer's machine before `git push`. For a repository connected to a Team with `teamProjectId`, you can check in CI that each pushed commit went through that hook. Add a separate step after the gate:

```yaml
- name: Check pre-push hook record
  if: always()
  run: npx @iris-code/cli@latest hook verify . --format github
  env:
    IRIS_LICENCE_TOKEN: ${{ secrets.IRIS_LICENCE_TOKEN }}
```

The gate keeps its own exit code. Hook verification always exits `0`: a missing record shows up as a warning and in the Team audit log, never as a failed build. It checks the latest commit on the pull request (the PR head SHA) rather than GitHub's temporary merge commit. See [Team governance](/teams/governance) for skip conditions and evidence limits.
