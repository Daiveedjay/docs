A coding agent asked to tidy up a large file can easily make it worse: it can break an import, remove something another file uses, or squeeze code onto fewer lines without simplifying anything.

Iris Code lets the agent get a refactor plan before it starts and check its edits afterwards. Iris Code supplies the project rules and checks the result; you or the agent still make and review the code changes.

There are three ways to connect them: the MCP server, terminal commands, and an optional check that runs when the agent finishes.

## MCP

MCP is the connection that lets a coding agent call Iris Code tools. Set it up using the [MCP server guide](/agents/mcp), then ask the agent to get a plan, make one reviewed change and verify it before continuing.

### Tools reference

| Tool | Contract |
|---|---|
| `iris_refactor_plan` | Read-only plan; returns a session `baseline_id`, fixes, ranked suggestions and coverage |
| `iris_verify_refactor` | Uses the session ID or disclosed Git HEAD fallback; returns reasons, metrics, disabled checks and correction |
| `iris_check` | Adds `refactorPlanAvailable`, a hint and a session baseline for size or complexity failures |
| `iris_fix_safe` | Existing preview, `preview_token` and apply flow for mechanical fixes |

In plain terms: the plan tool saves a copy of the code and gives it an ID, `baseline_id`. The verify tool compares the agent's edits with that copy, or with your last commit (Git HEAD) when there is no ID, and says which it used.

Planning and verifying one file are Free. A new folder or workspace plan uses one successful local project action. Applying that plan's approved fixes and verifying against its saved copy are included. Changing the saved starting point or asking for a different plan is new work. See [Free allowances](/free).

Every MCP server checks whether the agent is currently allowed to use Iris Code. The server keeps its own saved copy of the code, so an agent cannot hand it a replacement "before" version to compare against.

Files in a folder where the [agent handoff](/agents/mcp#organisation-and-repository-restrictions) is off are hidden from plans and verification details. The result shows only how many were withheld, as `withheldByPolicy`.

## CLI scanning

The CLI is the set of Iris Code commands you run in a terminal. An agent can run them too:

```bash
iris refactor src/handlers.ts
iris refactor src/handlers.ts --format json
iris refactor src/handlers.ts --verify
iris fix --safe src/handlers.ts
```

Planning from the CLI only reads your code. Each command is a separate process, and its saved copy disappears when it ends, so a later `--verify` compares against your last commit (Git HEAD) instead.

The [project rules](/agents/project-rules) Iris Code generates describe the same loop and work without MCP. They respect any fixes or suggestions you have disabled, and tell the agent to:

1. Apply the fixes Iris Code has proved safe.
2. Review suggestions in order.
3. Keep behaviour and exports unchanged.
4. Stop when the file passes.
5. Verify, then run tests.

## Finish verification

A finish hook is an optional check that runs when an agent tries to stop. If the agent's edits made things worse compared with a plan it is still working from, the hook sends it back to correct the problem. It works alongside the package guard and does not replace your tests.

```bash
iris hook agent install --target claude,codex --verify-on-finish
iris hook agent status
iris hook agent uninstall --target claude,codex --verify-on-finish
```

The `--verify-on-finish` flag adds this check alongside the package guard. In either editor, **Hooks** has a separate **Enable** control with the same multi-select agent choice, so you can set it up or remove it independently of the package guard.

Each agent signals "stop" and "keep going" differently:

| Agent | Event | Continuation |
|---|---|---|
| Claude Code | `Stop` | JSON `decision: block` with `reason` |
| Codex | `Stop` | JSON only; the hook exits zero and returns `decision: block` |
| Copilot CLI and VS Code | `agentStop` / `Stop` | One response carries both CLI fields and `hookSpecificOutput` |
| Gemini CLI | `AfterAgent` | JSON `decision: deny` with `reason` |
| Cursor | `stop` | `followup_message` requests another turn |
| Windsurf / Devin | Observe-only finish event | No finish hook installed; use rules, MCP or CLI |

Windsurf can report that an agent finished but cannot send it back, so no finish hook is installed there.

### Which plan it checks

The hook only checks a plan the agent got in its current conversation, from an Iris Code MCP server that is still running for the same workspace. It finds the plan's `baseline_id` in the agent's transcript, the record of the conversation.

The saved copy of your code stays in the server's memory. The only thing written locally is a small registry of connection details and plan IDs.

If the transcript is missing, empty or has been compacted (shortened by the agent), the hook does nothing. It does not guess a starting point or fall back to your last commit.

### What happens when it finds a problem

Only a `regressed` verdict sends the agent back with a correction. `not-improved` is a warning and does not stop it finishing.

The agent gets at most one correction per agent turn, meaning one request you sent it. That single correction is shared with [verification integrity](/features/verification-integrity), however many refactors the turn verifies.

`maxCorrections: 0` turns corrections off; a larger value does not add more. After the one correction, the hook asks the agent to stop and show you the verdict and its changes. The agent's own limits on repeated turns add another safeguard.

Cursor's stop response has no field for warnings, so they are written to the error output instead. The hook does not call an AI model or change the push or build gate.

Codex also needs hooks switched on in its local configuration, and the project hook approved. Agents can change how they record transcripts, so automatic matching is best effort. When it is not active, the agent can still verify explicitly.
