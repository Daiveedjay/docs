Every project organises code differently. Refactor settings let you turn off suggestions you do not want, say where moved code should go, and choose which checks run after an edit.

The shared, top-level settings are Free. Signing in also lets per-language custom settings take effect, whatever your monthly action balance. Changing settings does not start a plan.

## Configuration

Use [Config Studio](/configuration/config-studio) to edit shared settings visually, or add a `refactor` block to your project's `.irisconfig.json`. Start with the defaults and change only what your project needs.

For example:

- Turn off a suggestion with `disable`.
- Keep all work in existing files with `allowNewFiles: false`.
- Set where moved code belongs with `destinations`.

A public API change affects code that other files depend on, so it needs approval by default.

## Settings reference

| Key | Default | Behaviour |
|---|---|---|
| `disable` | `[]` | Suppress named fix or suggestion IDs |
| `destinations` | `{}` | Override constants, types, components, hooks and utils paths; kept local |
| `allowNewFiles` | `true` | Permit proposed destinations that need new files |
| `publicApiRequiresApproval` | `true` | Mark public API changes as needing approval |
| `ranking` | `["local", "cross-file", "changes-public-api"]` | Order risk tiers; include every tier once |
| `packing.minTokenRatio` | `0.6` | Number between 0 and 1 used by packing detection |
| `verify.packing` | `true` | Detect artificial line packing |
| `verify.commentOnly` | `true` | Refuse improvement credited only to comments or whitespace |
| `verify.importsResolve` | `true` | Check imports in touched files and new helpers |
| `verify.importCycles` | `true` | Check newly introduced cycles |
| `verify.removedExports` | `true` | Check removed imported exports and warn on API changes |
| `verify.newFindings` | `true` | Compare finding identities and severity |
| `maxCorrections` | `1` | `0` turns refactor corrections off; any larger value still allows at most one correction per agent turn, shared with verification integrity |

When settings come from more than one place, such as a shared config and a language block:

- A list, such as `disable`, replaces the inherited list rather than adding to it.
- `verify`, `destinations` and `packing` combine key by key.

Config Studio shows every shared setting and lets signed-in users edit language overrides. Resetting a language field there restores the inherited value. Destination paths belong to one repository, so they stay in that repository's own file.

A correction is the message that sends a coding agent back to fix a problem after verification. An agent gets at most one per request you send it, whatever `maxCorrections` says; see [Agent integration](/refactor/agents#finish-verification).

```json
{
  "refactor": {
    "disable": ["early-return", "merge-imports"],
    "allowNewFiles": false,
    "publicApiRequiresApproval": true,
    "packing": { "minTokenRatio": 0.8 },
    "maxCorrections": 1
  },
  "languages": {
    "go": { "refactor": { "disable": ["options-object"] } },
    "python": { "refactor": { "verify": { "importCycles": false } } }
  }
}
```

Without signing in, the shared `refactor` settings apply, but per-language overrides are ignored with a warning. The language keys are `typescript`, `javascript`, `go`, `python`, `ruby`, `csharp`, `java` and `rust`. Vue and Svelte use the language declared in their script.

Invalid refactor settings produce an error rather than silently using defaults. This helps you notice a setting that would otherwise appear to work.
