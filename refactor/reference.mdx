A refactor plan contains two kinds of change. Mechanical fixes are small edits you can preview and apply; structural suggestions are larger changes that you or a coding agent must review and make.

## Mechanical fixes

| ID | Trigger | Languages | Before and after |
|---|---|---|---|
| `merge-imports` | File length or too many imports | JS/TS, Vue/Svelte scripts, Python, Rust | Two compatible imports from one module become one |
| `remove-unused-import-name` | An unused imported binding | JS/TS | `{ used, unused }` becomes `{ used }` |
| `remove-unused-import` | A whole unused import | JS/TS, Java | Java and `import type` are removed. JavaScript keeps the module load as `import './a'`. A TypeScript value import is left for you |
| `remove-debug-statement` | An isolated debug call | All ten, where a statement is proved | A multiline debug statement is removed |
| `remove-unused-literal-variable` | An unused literal-only binding with proved local scope | JS/TS, Vue/Svelte scripts, Go, Python | The declaration is removed without evaluating an expression |

### Imports that need review

An **import** lets one file use code from another. Loading that other file can also run code, such as registering a plugin. Removing an unused name must not accidentally stop that work.

JavaScript keeps the module loading with a side-effect import, such as `import './a'`. TypeScript behaves differently depending on `verbatimModuleSyntax`, so Iris Code leaves a whole unused value import for you to review. A type-only import, written with `import type`, does not load a module and can be removed.

Vue and Svelte imports are kept because a component's template may use a name that appears unused in its script.

Iris Code also leaves these import combinations unchanged:

- A namespace import combined with a named import.
- Mixed type-import styles, or two type-only TypeScript imports.
- Rust `use` statements with an attribute or documentation comment.
- Side-effect imports, or imports with comments between the statements being merged.

### Variables that need review

A variable may be used by code outside the part Iris Code can check. Python class or module attributes and Go package variables are therefore kept.

JavaScript and TypeScript declarations at the top of a file are eligible only when the file is a module. Shared script declarations are kept because another script may use them.

### Debug statements that need review

A debug statement prints information while you work. Iris Code only offers to remove one when it can identify the complete statement without removing other work.

The fix is left for you when:

- The statement shares a line with other code, or its call is unfinished.
- Its arguments may do work, such as assigning a value, incrementing a counter, using `await` or calling something other than a simple formatter.
- It is the entire body of an `if`, `else`, loop or arrow function without braces.
- It is the last expression of a Ruby method, which can determine the return value.
- Removing it would leave a Go import or variable unused, or a Python block empty.

`console.error` reports errors and is never removed. Removing an unused function is a suggestion to review, rather than an automatic mechanical fix.

## Structural suggestions

| ID | Trigger and proposed change | Languages where built | Typical risk | Before and after |
|---|---|---|---|---|
| `extract-constants` | A large file with proved constants; move them to the observed constants location | Go, Ruby, Rust, Vue | Cross-file or public API | Inline declarations become a module with preserved exports |
| `move-function-cluster` | Related proved functions in a large file; move the cluster together | TS, JS, Python, Ruby, Java, Rust, Vue, Svelte | Cross-file or public API | A cluster becomes a module, with explicit imports and forwarding APIs |
| `move-types` | Type declarations in a large file; move them to the observed type location | TS, Go, Python, C#, Java, Rust, Vue | Cross-file or public API | Inline types become shared types |
| `split-declarations` | Independent proved declarations in a large file | All except Rust | Cross-file or public API | A file is split at complete declaration boundaries |
| `delete-unused-function` | A private or local function with no detected use | TS, JS, Ruby, C#, Java, Rust, Vue, Svelte | Local | Review and remove the complete function |
| `extract-function` | A proved executable block in a long function | Svelte | Local | Inline work becomes a helper with explicit inputs and outputs |
| `early-return` | A whole function body inside one condition | All except Python and Vue | Local | An outer condition becomes a guard and early return |
| `lookup-table` | A proved repeated condition or switch on the same value | TS, Java, Svelte | Local | Repeated scalar choices become a lookup |
| `options-object` | An ordered argument list exceeds its threshold | All ten | Public API | Positional arguments become a named options object |
| `move-imports-with-code` | Imports used exclusively by a moving cluster | TS, JS, Python, Java, Rust, Vue, Svelte | Cross-file | Imports move with the code that needs them |
| `extract-duplicate` | Two located executable duplicate blocks | Python, Ruby, Java, Vue | Cross-file | Both use a helper in their nearest common folder |
| `name-magic-numbers` | Located numeric code observations | Java | Cross-file | Values gain names chosen for their domain meaning |
| `consolidate-state` | Many local state hooks in a component | React JSX, Vue | Local | Related state becomes a coherent state object or reducer |
| `derive-without-effect` | A proved effect whose work is derived state | React JSX/TSX, Vue and Svelte | Local | A derived value is calculated without an effect |
| `extract-component` | A proved child markup subtree | React JSX/TSX and Vue | Cross-file | Markup becomes a component with explicit props |

Check the risk shown on your actual suggestion. The table gives typical risks, but the effect depends on your code.

A **public API** is code that other files or projects depend on. Changing an exported name or the arguments a function accepts can be marked `changes-public-api`; by default, this needs approval.

The estimated effect is a guide to the size of the change. It does not promise that the gate will pass, and overlapping parts of the code are counted only once.

Iris Code leaves a change for review when it cannot identify the complete code to move. This includes some functions called indirectly by a framework, related metadata outside the identified code, and syntax it does not support.

See the [language coverage table](/refactor/language-coverage) before relying on a particular suggestion.
