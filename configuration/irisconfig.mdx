The `.irisconfig.json` file holds your project's Iris Code settings: what to check, and the limits (thresholds) code must meet. Commit it with your code so everyone gets the same results in the editor, on the command line and in automated checks such as CI.

For each file, Iris Code uses the nearest `.irisconfig.json` in its folder or the folders above it. That lets separate packages in a large repository have different settings.

<Note>
  This page lists **settings you can change**, not the rules Iris Code checks. It mixes gate
  limits, thresholds, scoring weights, severity overrides and rule ids, so counting the
  entries here does not give the number of rules. For that, see the
  [accuracy benchmark](/trust/accuracy-benchmark), which publishes every measured rule
  per language.
</Note>

<Note>
  **Priority order:** nearest folder `.irisconfig.json` → workspace root `.irisconfig.json` → personal default → VS Code settings → built-in defaults
</Note>

## Comments, autocomplete and hover help

`.irisconfig.json` is JSONC, which is JSON that allows `//` comments. Every config Iris Code writes includes comments explaining each setting, so you can read the file without this page open.

Generated configs also open with a `$schema` line:

```json
{
  "$schema": "https://www.iriscode.co/schema/v1/irisconfig.schema.json"
}
```

That line points your editor at a description of every valid setting, called a JSON Schema. With it, you get autocomplete on every field and a squiggle when a value is wrong, in VS Code, JetBrains, Neovim or any other editor that supports JSON Schema. No plugin is needed. Keep the line if you edit the file by hand.

**Hover over any setting to see what it does.** That text comes from the schema bundled with your installed version of Iris Code, not downloaded from us. It works offline and behind a proxy, and it always describes the version you are actually running rather than the newest release.

<Warning>
  **JetBrains IDEs:** if `.irisconfig.json` reports "JSON standard does not allow comments", your IDE has a saved user setting that cancels the file type Iris Code registers for this file. Reinstalling the plugin will not clear it. See [the fix in the installation guide](/installation#json-standard-does-not-allow-comments).
</Warning>

## Config presets (Free + Pro)

A preset is a ready-made set of limits. Rather than choosing every threshold yourself, start from one: add `presetId`, commit the file, and the whole team uses the same settings.

```json .irisconfig.json
{
  "presetId": "legacy"
}
```

Available presets: `strict`, `balanced`, `legacy`, `security`, `typescript`, `ai-assisted`.

The `ai-assisted` preset sets stricter limits for teams reviewing a lot of AI-assisted code. It limits duplicate blocks and suppressions, but does not impose a naming convention.

Configs that Iris Code generates explain each active check and gate limit with a one-line comment. Settings that depend on your team, such as naming conventions, ignore lists and per-language settings, are included as commented-out examples until you choose them.

<Tabs>
  <Tab title="Without sign-in">
    Iris Code uses the preset's values exactly as shipped. Without signing in, changes you make to threshold fields in the file are ignored, and the editor marks them with a yellow warning squiggle. The preset built into Iris Code decides the values, not the file on disk.
  </Tab>
  <Tab title="Signed in">
    The preset is the starting point, and you can change any threshold on top of it. This works for signed-in Free users as well as paid users. Your changes keep working after your monthly project actions run out, and editing or saving the config does not use an action.
  </Tab>
</Tabs>

## Full custom configuration

For complete control, you can write out every setting. Every key is optional, so include only the ones you want to change.

```json .irisconfig.json
{
  // Thresholds - structural size limits
  "functionLengthThreshold": 40,
  "fileLengthThreshold": 300,
  "maxFunctionsPerFile": 10,
  "maxImportsPerFile": 8,
  "maxParameterCount": 5,
  "complexityThreshold": 7,

  // Detection toggles - turn individual rule categories on or off
  "enableConsoleLogWarnings": true,
  "enableMagicNumberDetection": true,
  "enableTodoDetection": true,
  "enableLongParamDetection": true,
  "enableUnusedDetection": true,
  "enableMissingReturnTypeWarnings": true,
  "enableSecretsDetection": true,
  "enableSecuritySmells": true,
  "enableDuplicateDetection": true,
  "duplicateBlockMinTokens": 40,

  // Display - UI and sidebar options
  "enableCodeLens": true,
  "enableStatusBar": true,
  "enableInlineDiagnostics": true,
  "inlineDiagnostics": {
    "hardcodedSecrets": true,
    "errorWarnings": false,
    "warningLevelWarnings": false,
    "tsIgnore": true,
    "unusedFunctions": true,
    "anyUsage": true,
    "consoleLogs": false,
    "magicNumbers": false,
    "longParamLists": false,
    "unusedVars": false,
    "todos": false
  },
  "sidebarFontSize": 14,

  // Gate thresholds - used by the CLI and git pre-push hook
  "minHealthScore": 70,
  "gateMaxSecrets": 0,         // Signed-in configuration - max hardcoded secrets workspace-wide
  "gateMaxComplexity": 12,     // Signed-in configuration - max complexity score per file
  "gateMaxFileLength": 500,    // Signed-in configuration - max line count per file
  "gateMaxSmellsPerFile": 8,   // Signed-in configuration - max total smells in a single file
  "gateMaxSecuritySmells": 0,  // Signed-in configuration - max security smells workspace-wide
  "gateMaxSuppressions": 5,    // Signed-in configuration - max iris-ignore suppressions per file
  "gateMaxDuplicateBlocks": 0, // Signed-in configuration - max duplicate code blocks across the scan
  "gateMaxNamingViolations": 0,// Signed-in configuration - max naming violations across the scan
  "gateMaxParseErrors": 0,     // Signed-in configuration - max unparseable files (unset = report, never block)
  "ignoreSuppressions": false, // Signed-in configuration - treat all iris-ignore directives as inert

  // Ignore rules - skip files or functions from analysis
  "ignoreFiles": [
    "**/*.test.ts",
    "**/*.spec.ts",
    "**/generated/**"
  ],
  "ignoreFunctions": [
    "main",
    "handler"
  ],
  "testConvention": "colocated",

  // Severity overrides - change the severity level per rule
  "severityOverrides": {
    "file-too-long": "warning",
    "function-too-long": "warning",
    "too-many-functions": "warning",
    "too-many-imports": "warning",
    "no-exports": "warning"
  },

  // Scoring weights - points deducted per finding type
  "healthScoreWeights": {
    "hardcodedSecret": 10,
    "errorWarning": 5,
    "warningWarning": 3,
    "anyUsage": 2,
    "tsIgnore": 3,
    "consoleLog": 1,
    "deepNesting": 2,
    "longParamList": 1,
    "unusedVar": 1,
    "unusedFunction": 2
  }
}
```

### Thresholds

These keys set the size limits, such as how long a function may be, that produce warnings in the editor and sidebar.

| Key | Default | What it controls |
|-----|---------|-----------------|
| `functionLengthThreshold` | `40` | Lines before a function is flagged. In `.jsx`/`.tsx`, JSX markup does not count toward this: a component is measured by its logic, the same way a Vue or Svelte `<template>` never counted. `fileLengthThreshold` still counts every line, so a large component is still flagged as a long file |
| `fileLengthThreshold` | `300` | Lines before a file is flagged. Statements joined onto one line count as separate lines; see [how length is counted](/features/file-analysis#how-length-is-counted) |
| `maxFunctionsPerFile` | `10` | Max functions before the file is flagged |
| `maxImportsPerFile` | `8` | Max third-party imports before flagging |
| `maxParameterCount` | `5` | Max parameters before a function is flagged |
| `complexityThreshold` | `7` | Complexity score that triggers a status bar warning |

### Detection toggles

Turn individual kinds of check on or off, without removing findings from the sidebar entirely.

| Key | Default | What it controls |
|-----|---------|-----------------|
| `enableConsoleLogWarnings` | `true` | Flag `console.log` / `print()` / `fmt.Print*` |
| `enableMagicNumberDetection` | `true` | Flag raw numeric literals without a named binding |
| `enableTodoDetection` | `true` | Flag `TODO` / `FIXME` / `HACK` comments |
| `enableLongParamDetection` | `true` | Flag functions with too many parameters |
| `enableUnusedDetection` | `true` | Flag unused variables and functions |
| `enableMissingReturnTypeWarnings` | `true` | Flag exported functions missing return types (TS/JS only) |
| `enableSecretsDetection` | `true` | Enable two-layer hardcoded credential scanning (JS/TS, Go, Python) |
| `enableSecuritySmells` | `true` | Enable the nine [security smell](/features/security-smells) patterns (eval usage, SQL concatenation, insecure RNG, and the rest) |
| `enableDuplicateDetection` | `true` | Detect duplicated code blocks within and across files via normalised token-window matching |
| `duplicateBlockMinTokens` | `40` | Minimum normalised-token run length before two stretches of code count as a duplicate block (min `10`) |

### Display

Control what Iris Code shows in the editor.

| Key | Default | What it controls |
|-----|---------|-----------------|
| `enableCodeLens` | `true` | Show inline Code Lens hints |
| `enableStatusBar` | `true` | Show the Iris Code item in the status bar |
| `enableInlineDiagnostics` | `false` | Master toggle for squiggles and Problems panel entries |
| `sidebarFontSize` | `14` | Base font size in pixels (10 to 20) for the Iris Code sidebar and detached panel |

Inline diagnostics are the squiggles under code and the entries in the Problems panel. Once `enableInlineDiagnostics` is `true`, the `inlineDiagnostics` object turns individual categories on or off.

### Gate thresholds

A gate is the pass or fail decision made when your code is checked by the CLI (the `iris` terminal commands) or the git pre-push hook. These keys set its limits. A file or workspace that goes over a limit fails the check.

| Key | Tier | What it controls |
|-----|------|-----------------|
| `minHealthScore` | Free + Pro | Files below this score are considered failures |
| `gateBaselineMode` | Signed in | Judges each existing file against its own score in your locked baseline (a saved snapshot of scores) instead of `minHealthScore`. New files still use `minHealthScore`. Useful for stopping older code getting worse without requiring a full cleanup first. |
| `trendRegressionThreshold` | Signed in | Highlights drops in the Trends table when a file falls by more than this many health-score points between snapshots. Smaller drops can still show as declining; this key controls what Iris Code calls out as a notable regression. |
| `gateMaxSecrets` | Signed in | Max hardcoded secrets allowed workspace-wide. Set to `0` to require a clean workspace |
| `gateMaxComplexity` | Signed in | Max complexity score per file; exceeding it fails the gate regardless of health score |
| `gateMaxFileLength` | Signed in | Max line count per file; works alongside `fileLengthThreshold` (which controls warnings) |
| `gateMaxSmellsPerFile` | Signed in | Max total smells in a single file (console logs, magic numbers, long param lists, unused vars/functions, TODOs) |
| `gateMaxSecuritySmells` | Signed in | Max security smells allowed workspace-wide (eval usage, SQL injection risk, insecure RNG, disabled TLS, weak hashing, and the rest of the nine patterns). Set to `0` to require a clean workspace |
| `gateMaxSuppressions` | Signed in | Max [inline suppressions](/enforcement/suppressions) (`iris-ignore` comments) allowed in a single file, so a file cannot silence too much before the gate fails. Defaults to `5` on the `strict` preset and `3` on `security`; unset elsewhere |
| `gateMaxDuplicateBlocks` | Signed in | Max duplicate code blocks across the whole scan (a block spanning two files counts once). Set to `0` to require a duplication-free codebase. Only counts blocks when `enableDuplicateDetection` is on |
| `gateMaxNamingViolations` | Signed in | Maximum [file naming](/configuration/file-naming) violations across the scan. |
| `gateMaxParseErrors` | Signed in | Maximum files Iris Code could not read (parse). **Unset by default, so an unreadable file is reported without failing the gate.** A real syntax error is already caught by your compiler and your build, where Iris Code adds nothing. Set to `0` to treat any unreadable file as a failure. Unreadable files are left out of the workspace average either way, so they never pull your score down |
| `ignoreSuppressions` | Signed in | Set to `true` to ignore every `iris-ignore` comment, so suppressed findings count again. A switch for team leads, for audits or when suppressions are being overused |

### Ignore rules

| Key | What it controls |
|-----|-----------------|
| `ignoreFiles` | Glob patterns for files to skip entirely in workspace analysis |
| `ignoreFunctions` | Function names Iris Code should never flag, regardless of length or complexity |
| `testConvention` | Where Iris Code looks for test files: `"colocated"` (default), `"dedicated"`, or `"both"` |

### Scoring weights

`healthScoreWeights`, available when you are signed in, lets you override how many points each finding type subtracts from the base 100 health score. See [Scoring Weights](/configuration/scoring-weights) for the full reference and examples.

### Per-language config

A repository that mixes languages rarely wants one set of limits for everything. For example, you may want to allow 500-line Python modules while keeping TypeScript files to 300 lines.

The `languages` block changes per-file settings separately for `typescript`, `javascript`, `go`, `python`, `ruby`, `csharp`, `java`, and `rust` files. Anything you do not set there uses the main settings.

`.tsx` files count as TypeScript and `.jsx` / `.mjs` / `.cjs` as JavaScript.

A `ruby` block also governs the extensionless Ruby files Iris Code reads, such as `Gemfile` and `Rakefile`; a `csharp` block governs both `.cs` sources and `.csproj` project files; and a `java` block governs both `.java` sources and the `.properties` files Iris Code reads for credentials.

```jsonc
{
  "fileNaming": {
    "convention": "kebab-case",
    "ignore": [],
    "overrides": [
      { "files": ["**/components/**"], "convention": "PascalCase" },
      { "files": ["**/hooks/**", "**/composables/**"], "convention": "camelCase" }
    ]
  },
  "fileNamingScope": "new-files",
  "fileLengthThreshold": 300,
  "languages": {
    "python": {
      "fileLengthThreshold": 500,
      "fileNaming": { "convention": "snake_case", "scope": "all", "ignore": [] }
    },
    "typescript": {
      "functionLengthThreshold": 35,
      "fileNaming": { "convention": "kebab-case", "ignore": ["src/legacy/**"] }
    },
    "go": { "functionLengthThreshold": 60, "gateMaxSmellsPerFile": 3 }
  }
}
```

Top-level `fileNaming`, its ordered `overrides`, and `languages.*.fileNaming` are Free. Path overrides are checked in order and the last match wins. When no path rule matches, the language's own naming policy is used if it has one, for compatibility with older configs; otherwise the top-level convention applies. Top-level ignore patterns always apply.

When you are signed in, you can also set per-language thresholds, `healthScoreWeights`, `severityOverrides` and gate limits. These keep applying to the file checks you can run after your monthly project allowance is used up. Setting a threshold does not give you paid enforcement or start a scan.

Set top-level `fileNamingScope` to `"new-files"` (default) or `"all"`. A matching path rule can override it with `scope`; a language's naming policy can do the same when no path rule matches. See [File naming conventions](/configuration/file-naming) for the full order of rules, how the baseline is used, suggestions, ignore patterns and exemptions.

Some settings only make sense for the whole project, so they are refused inside a language block with a warning: limits that count across the whole scan (`minHealthScore`, `gateMaxSecrets`, `gateMaxSecuritySmells`, `gateMaxDuplicateBlocks`, `gateMaxNamingViolations`, `gateMaxParseErrors`), `presetId`, and the `enable*` switches.

Which setting applies to a file is worked out in one shared place, so the sidebar, CLI, git hook, build hook and CI always agree. The sidebar's file tab shows the language setting in use next to where the config came from (for example "Workspace config · Python override"). `iris gate` prints the limit that applied to each failing file, plus a "Per-language overrides active" note.

An unknown language key, such as an `elixir` block written for a newer Iris Code release, produces a warning and is skipped, so a newer config does not break an older installation.

A per-file gate limit set only inside a language block still applies to files of that language, even when no top-level limit is set.

## Package guard (Free)

A package is code written by someone else that your project uses. The `packageGuard` block sets what the [package guard](/agents/package-guard) stops when a coding agent, `iris install` or a push adds one. It is a safety policy rather than a threshold, so it works on every plan and presets do not restrict it.

```jsonc
{
  "packageGuard": {
    "onUnchecked": "warn",
    "blockSeverity": "high",
    "minimumReleaseAgeDays": 7,
    "allow": [{ "name": "left-pad@1.3.0", "reason": "Pinned by the legacy build, SEC-41" }]
  }
}
```

- `onUnchecked` (`"warn"` or `"block"`) decides what happens to a package the guard could not check.
- `blockSeverity` sets the lowest severity of known security problem (advisory) that blocks. A report that a package is malicious always blocks.
- `minimumReleaseAgeDays` blocks versions released fewer than that many days ago.
- Each `allow` entry needs a `reason`, or it is ignored and reported as an error.
- `prePush: true` adds a check of your lockfile, the file listing exact package versions, to the git hook. This needs Pro.

## Refactor policy (Free)

The `refactor` block controls suggested fixes, where moved code should go and the checks run afterwards. Top-level settings work on every plan, whatever your preset. Signing in also lets you set them per language; saving them does not use a project action.

```jsonc
{
  "refactor": {
    "disable": ["early-return"],
    "destinations": { "types": "src/types" },
    "packing": { "minTokenRatio": 0.6 },
    "verify": { "importCycles": true },
    "maxCorrections": 1
  }
}
```

A `refactor` block with mistakes in it is reported, rather than quietly replaced with defaults. [Refactor configuration](/refactor/configuration) lists every key and its default.

## Severity overrides

Severity is how serious a finding is reported as. Use the `severityOverrides` object to change it for a kind of warning in this project. Each key accepts `"error"`, `"warning"`, or `"info"`.

| Warning key | Valid severities |
|-------------|-----------------|
| `file-too-long` | `error` · `warning` · `info` |
| `function-too-long` | `error` · `warning` · `info` |
| `too-many-functions` | `error` · `warning` · `info` |
| `too-many-imports` | `error` · `warning` · `info` |
| `no-exports` | `error` · `warning` · `info` |

<Tip>
  Only include keys you want to change. Anything you leave out comes from the preset (if set), then VS Code settings, then built-in defaults.
</Tip>

## Packed code integrity (Free)

Squeezing several statements onto one line can sneak a file under a length limit. [Verification integrity](/features/verification-integrity#packed-code) reports this as `code-packed`. `codePackedThreshold` sets how many newly joined statements a file must have before that is reported.

It defaults to `3` and accepts whole numbers of `1` or more. Every preset and language uses the same top-level value; a `languages` block cannot change it.

```json
{
  "codePackedThreshold": 5
}
```

The check reads this value from the starting point it compares against, not from the change itself. So raising the threshold in a change does not weaken the check on that change, and the increase is itself reported as `rules-loosened`.

The rule warns by default. `severityOverrides["code-packed"]: "error"` makes it block pushes and CI. Use `"info"` for the quietest severity, and `ignoreFiles` for generated files.

## Agent handoff

MCP is a connection that lets a coding agent call Iris Code's tools. `agentHandoff` is a Free `true`/`false` setting. Set `"agentHandoff": false` to turn off the Iris Code MCP tools that read this repository, for everyone using it.

It is read fresh on every tool call, including for Free users. `true`, or leaving the key out, adds no restriction for the repository and cannot loosen a rule set by your organisation. The package guard stays available either way.

See [Team governance](/teams/governance).

## Schema graph (Free)

`schemaGraph` controls the [Schema graph](/features/schema-graph), the diagram of your database tables. It is on by default and skips files in your ignore rules. Presets do not affect it, so a Free preset never removes the sources you chose.

```json
{
  "schemaGraph": {
    "enabled": true,
    "sources": [
      { "source": "sql", "paths": ["db/migrations"], "dialect": "sqlite" }
    ]
  }
}
```

Leave out `sources` and Iris Code finds your schema files automatically. To choose them yourself, list each `source` (`prisma`, `sql`, `drizzle`, `django`, `rails` or `diesel`) with its `paths`, relative to the project. `dialect` applies only to SQL and accepts `postgres`, `mysql` or `sqlite`.

Set `enabled` to `false` to turn the schema graph off. Invalid source paths are refused rather than read from outside the project.
