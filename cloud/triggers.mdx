A trigger is an event that starts a cloud scan automatically, such as a change reaching your main branch. Each completed scan uses one scan from your allowance.

You choose triggers for each repository, balancing how quickly you see results against how many scans you use.

## The two triggers

<CardGroup cols={2}>
  <Card title="Audit merges" icon="git-merge">
    **Off by default.** One audit each time a change lands on your default branch. This is what keeps a project's score current.
  </Card>
  <Card title="Audit pull requests" icon="git-pull-request">
    **Off by default.** One audit each time a pull request is updated, so an active branch costs several. Catches problems before they land.
  </Card>
</CardGroup>

## Why repositories start in manual mode

Both triggers start off, so connecting a repository does not sign you up for repeated scans. Importing it starts one scan. After that, you decide whether to scan by hand or turn on automatic triggers.

Free users can turn on either trigger, within the same monthly cloud allowance. Scans stop when it is used up.

The two triggers cost very different amounts:

- A merge trigger fires once for each change that lands on the default branch.
- A pull request trigger fires on every push to the branch. A pull request with eight commits pushed one at a time costs eight audits, and merging it costs one more.

<Warning>
  If you are trying to spend less, **turning pull request auditing on is the wrong choice**. It is the expensive setting, usually several times the volume of merges alone. Auditing merges only is the cheapest setting that still keeps a score current.
</Warning>

## Changing them

Open the repository from **Projects** and use the **When to audit** panel. Each row says what it costs as well as what it does.

Turning both off is a valid choice, and the screen says plainly what it means: nothing is audited automatically, and the project's score changes only when you run an audit yourself.

## Pausing, which is different

Pausing a repository stops **every** automatic audit, whichever triggers are on, while audits you start by hand still work. Use it to keep the connection and the history but stop scans for a while.

Resuming brings back the triggers the repository already had; pausing does not reset them.

## Rapid pushes are collapsed

Pushing several times in quick succession does not cost an audit each time. If an audit is still waiting to run for the same pull request or the same default branch, a newer push replaces it, and the replaced audit is **not** counted against your allowance. Only the audit that actually runs is counted.

The window for this is short, about twenty seconds, so it catches a quick burst of pushes rather than a normal working day. Thirty pushes spread across an afternoon are thirty separate changes and cost thirty audits.

## What is never charged

An audit that produced no report does not count against your allowance:

- One you cancelled
- One replaced by a newer push to the same branch or pull request
- One no scanner ever picked up, or that timed out
- One stopped because the repository was paused, or because GitHub access ended

<Note>
  There is also a safety limit of 50 audits per repository per day. It stops a misconfigured CI loop using a month's allowance in an afternoon, and sits well above any normal day. If you hit it, something is looping.
</Note>

## Manual audits

You can always run an audit by hand from the project screen, whatever the triggers say and even while the repository is paused. It costs one scan like any other.

<Tip>
  Start in manual mode while you learn how many scans you need. If your cloud allowance covers it, turn on merges for the repositories you want to track. Turn on pull requests only where you need earlier feedback and have room for the extra scans.
</Tip>
